## Legacy local editorial catalog

`catalog/jobs.json` supplies the sample seed and remains the publishing source for the legacy Node server. Next.js uses Postgres when configured. IDs must remain stable. Each record contains the canonical employer URL, public sanitized description, editorial assessment, work focus, separate SWE gate, published compensation semantics, workplace, logo, status, and employer check timestamp. Validate edits with:

```sh
pnpm board:catalog check
```

Add reviewed roles by adding records matching the existing schema. Use `draft` while reviewing. Read qualifications and responsibilities against `CATEGORY_DEFINITION.md`; confirm current source status, location, compensation, and whether the source expressly forbids full-text reuse. Sanitize descriptions to the schema's attribute-free formatting tags before importing them. Catalog errors fail explicitly; they do not fall back to unvalidated postings. The server rereads the catalog for each request, so a saved catalog change is visible on reload.

After actually checking an employer posting, publish using its check time:

```sh
pnpm board:catalog publish <id> <verified-at-ISO-timestamp>
pnpm board:catalog close <id>
pnpm board:catalog draft <id>
```

`publish` requires a non-future timestamp from within seven days. Published listings older than seven days are withheld until rechecked; drafts and closed listings are withheld immediately. Existing open tabs are snapshots and refresh to see changes. This first version has no automatic source monitor. `sample` records remain visible with a prominent sample-inventory notice; the six seeded records preserve the design snapshots and are not claims of fresh availability. Remove them or freshly verify and publish them before a public launch.

## Legacy local feedback

Feedback is written to ignored local `data/board/feedback.jsonl`. A random HttpOnly, SameSite cookie associates state with the visitor, so it survives reload and supports undo; no account or contact details are collected. It is an editorial-review signal and does not automatically remove a role. Test activity is recorded like any other local activity.

```sh
pnpm board:catalog feedback
```

Fold events by visitor and job ID, retaining the latest `active` value, when reviewing current flags. The POST endpoint checks same origin, limits request size, validates visible job IDs, and applies a small in-process rate limit. Feedback errors are shown to readers. The file must live on persistent storage if deployed; this implementation has no multi-server datastore or authenticated editor UI.

### Ordering

The initial board orders by recency, newest first. Use the employer's original publication date when reliably available; otherwise use our first-seen timestamp. Preserve timestamp provenance. Keep original publication, repost/update, first-seen, last-checked, and board-publication timestamps distinct: refreshing, reclassifying, or approving an existing posting must not make it appear newly posted. ### Durable records and publishing rules

- **Employer sources and runs:** retain employer identity, source adapter, canonical board URL, run outcomes, completeness, request usage, and last successful collection. Bound concurrency, retries, and API spending. A failed or incomplete fetch is unknown availability, not evidence of closure.
- **Source postings and versions:** identify postings by source, employer, and employer posting ID where available, with canonical URL fallback. Retain permitted source descriptions, sanitized display HTML, attribution, timestamps, and content hashes. Repeated collection must be idempotent. Preserve source versions separately from normalized fields and editorial interpretation.
- **Duplicates and grouping:** preserve each source posting, application URL, location, and compensation. Link mirrors to a preferred employer posting reversibly; do not delete evidence. Distinct openings with the same employer/title are not automatically duplicates. Any future display grouping must preserve access to each opening and its application link; title/company equality alone cannot merge jobs.
- **Location and compensation:** model physical locations and their work arrangements separately from remote eligibility. Preserve explicit eligible countries/states, timezone restrictions, and unknown values. Support roles offering both office and remote options without inferring eligibility from headquarters. Preserve location-specific salary bands, currency, period, and base-versus-other semantics; do not synthesize a misleading combined range.
- **Assessments:** attach category fit, open-vocabulary focus, separate SWE experience gate, exact evidence, model/rules/reference versions, and assessment time to a specific posting version. Reassess material changes; model output must not silently overwrite editorial decisions.
- **Editorial decisions and publication:** record approve/reject/defer decisions and overrides with actor, timestamp, and assessed version. Initially new roles require review before publication. Detect changed responsibilities or qualifications and route them back to review. Publication state is distinct from source availability and classification state.
- **Feedback:** distinguish “not a builder role” from “closed or broken posting.” Preserve visitor isolation and undo. Reports trigger the appropriate review or source check rather than directly changing publication state.
- **Evaluation:** keep calibration references separate from frozen fresh evaluation batches. Measure incorrect inclusions and missed positives by sampling both proposed inclusions and rejected candidates. Report sample size and uncertainty; do not infer complete coverage from a clean accepted list.
